# 判断样本 · thinking-lenses 模式 E 拆分为 9+1 子模式

## 元信息
- 日期：2026-07-20
- 场景类型：工作（skill 设计决策）
- 协作对象：把 thinking-lenses 技能的模式 E（内容审查）从 5 透镜一刀切，拆分为 9+1 子模式
- 提取范围：当前对话全程（3 轮 AskUserQuestion + 6 个文件改动 + 验证）

## 判断样本

### Q1 · 否定了什么

- **否定了方案 C「核心 5 透镜 + 4 专项 + 6 场景预设」（AI 推荐方案）**——具体特征：保留原 5 透镜常驻 + 按场景叠加专项透镜。否定的不是"分层思路"本身，是这种分层会导致**场景预设和核心透镜大量重叠**（核心 5 里已经有 Novelist/Designer，场景预设的 PPT 又强化这两个，没制造真正的视角切换）
- **否定了方案 D「最小拆分 3+1」**——具体特征：只拆内容/人际/决策三大类。否定的是**颗粒度不够区分业务**：数据分析、PPT、邮件、制度在"内容"类下会被同一套透镜处理，退回到一刀切的同类问题
- **否定了 E9 走「工程实践型」方向**——具体特征：用 Programmer+Soldier+Engineer+Hacker 审代码风格/错误处理/架构。否定的是**与已有 code review skills 重叠**——E9 会变成 code review 的低配版，失去独立存在的理由
- **否定了「纯模板」（0 示例）深度**——具体特征：所有子模式只用统一模板，不配示例。否定的是**模板缺乏锚点**——用户看到"输出必须包含 X"不知道 X 长什么样，会和原 SKILL.md 一样停留在抽象描述
- **没有否定方案 A**（场景细分型 8+1）——但在实施时把 8 改成了 9，把代码审查作为可选子模式纳入

### Q2 · 为什么否定

- **方案 C（核心+专项+预设）** → 机制层：AI 默认"平衡倾向"——给方案时倾向推荐"兼顾精准度和维护成本"的中间方案。但平衡方案的隐患是**视角重叠**：核心透镜和场景预设共享多个透镜，实际审查时还是同一套视角在打转，看似有分层实际没切换。冲突：AI 的平衡倾向 vs "铁律 2：透镜间不重复角度"
- **方案 D（最小拆分）** → 机制层：AI 默认"最小改动倾向"——能用 3 类就不用 9 类。但最小拆分的代价是**业务失真**：用户的实际工作场景至少有 8 类（方案/制度/汇报/PPT/邮件/数据/人际/决策），压到 3 类会把性质完全不同的内容塞进同一个筐。冲突：最小改动倾向 vs 场景颗粒度对齐业务真实复杂度
- **E9 工程实践型** → 机制层：AI 默认"功能对齐倾向"——看到"代码审查"就想到行业主流的 code review。但 thinking-lenses 的定位是思维框架不是工程工具，走工程实践会与现有 code review skills 直接竞争，且没有专业工具（如 lint/AST）做支撑。冲突：主流对齐倾向 vs skill 定位差异化
- **纯模板（0 示例）** → 语境层：AI 默认"抽象优先"——先给规则再考虑例子。但这个 skill 的 SKILL.md 已经有大量"反例对照"（浅层做法❌/深层做法✅），证明例子是这个特定 skill 的核心教学方式。抽掉例子等于抽掉 skill 的教学机制

### Q3 · 保留了什么

**胜出方案的关键判别特征**：
- **场景对齐业务**：9 个子模式直接对应 work-detail.md 里盘点的 8 类高频产出 + 1 类代码审查（可选），每个子模式都有真实工作场景背书
- **每子模式必有"失败信号"**：不是泛泛检查点（"注意事实核查"），而是"这种内容最容易怎么死"（如方案审查的失败信号是"建成后状态模糊"）——失败信号比检查点更可执行
- **增量不改存量**：E0 兜底完整保留原 5 透镜组合，只是改名为"通用兜底"，不破坏现有引用链
- **5 透镜硬编码 5 处全改**：不只是改 SKILL.md，同步改 usage_guide/output_style/cognitive_principles/lens_matcher.py——避免"改了一处漏了四处"的不一致

**区别于被否定版本的核心差异**：不是"分层（方案 C）或合并（方案 D）"，而是"按业务场景的实际产出类型切分，每个子模式配专属失败信号"

### Q4 · 真正关心的问题本质

- **表层需求**：把模式 E 拆得更细
- **实际校验**：拆完之后，每个子模式能不能在用户说"帮我审一下 XX"时，**自动识别并切到正确的子模式**，而不是让用户自己选——识别精度决定拆分是否真有价值（否则就是多了 10 个标签的同一套流程）
- **更深一层隐含校验**：拆分会不会让 SKILL.md 膨胀到失去"按需加载"的设计哲学？通过把详细内容下沉到 audit_modes.md、主文件只保留速查表+决策树来解决——拆分的颗粒度上去了，但主文件的精简度保住了

### Q5 · 下次类似任务的判断顺序 + 避免误判

**判断顺序**（下次拆分任何 skill 的子模式时按此排查）：
1. 先盘点真实业务场景 → 从 work-detail 或实际产出物类型反推，有几类性质不同的内容
2. 每类配专属"失败信号" → 不是检查点清单，是"这种内容最容易怎么死"
3. 检查透镜组合的异质性 → 子模式之间透镜集合重叠度不能超过 30%（铁律 2 的跨子模式版本）
4. 验证识别机制 → lens_matcher 或决策树能不能自动选对子模式（不是让用户选）
5. 守 SKILL.md 精简 → 详细内容下沉到独立 reference 文件，主文件只留速查表+决策树
6. 同步所有硬编码点 → grep 搜索被改透镜组合的所有出现位置，全改

**避免误判**：
- 下次遇到"要不要拆分 X"，先问"X 的真实业务场景有几类性质不同的内容"——能数出 ≥4 类就值得拆，≤3 类用方案/字段切换更合适
- 下次给用户拆分粒度选项时，AI 的"推荐平衡方案"要警惕——平衡方案常因视角重叠失去拆分意义
- 下次新增子模式时，先问"这个子模式有没有独立的失败信号"——失败信号和别的子模式重复 = 没必要独立
- 下次新子模式涉及与已有 skill 重叠的功能（如 E9 代码审查 vs code review skills），先问"两者定位差异是什么"——没有明确差异就不要加

### Q6 · 关键变量

- **场景颗粒度对齐度** → 拆分的子模式数量是否对齐业务真实场景的多样性。决定拆分是否有价值——颗粒度粗于业务（如 3 类装 8 类内容）会退回一刀切，颗粒度细于业务（如 15 类细分到 PPT 每种风格）会增加维护成本无对应收益
- **失败信号独立度** → 每个子模式的"这种内容最容易怎么死"是否和别的子模式不同。决定子模式是否有独立存在理由——失败信号重复 = 视角同构 = 不需要拆
- **自动识别精度** → 系统能否根据内容关键词/特征自动选对子模式。决定拆分是真增量还是标签游戏——识别不准时用户还得手动选，拆分价值打折
- **主文件精简度** → 拆分后 SKILL.md 是否仍符合"按需加载"设计哲学。决定拆分的可持续性——主文件膨胀会让 skill 启动变慢、AI 加载成本上升
- **硬编码同步度** → 被改透镜组合的所有出现位置是否全改。决定一致性——漏一处就会出现行为和文档不符

## 价值标记
- 可复用度：高（"场景对齐业务 + 失败信号独立 + 自动识别 + 主文件精简 + 硬编码同步"可迁移到任何 skill 的子模式拆分）
- 通用规则：拆分 skill 子模式时，颗粒度对齐业务真实场景（不是 AI 推荐的平衡值），每个子模式配独立的"失败信号"（不是泛泛检查点），识别机制必须自动（不是让用户选），详细内容下沉到 reference 保主文件精简
- 最小验证动作：下次拆分任何 skill，先问"这个 skill 的真实业务场景有几类性质不同的内容"——能数出 ≥4 类且每类有独立失败信号才值得拆，否则用字段切换
- 升级判断：暂不升级。理由：这是 skill 子模式拆分场景的首次样本，未跨场景验证；"场景对齐业务 + 失败信号独立"虽强但需观察是否在所有拆分场景都成立（如纯工具类 skill 可能不需要失败信号）。按层 3 标准，需同类判断在 INDEX 出现 2-3 演进次才升级
